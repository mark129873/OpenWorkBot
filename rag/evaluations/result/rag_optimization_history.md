# OpenWorkBot RAG 优化历程

本文根据挂在 OpenWorkBot 项目下的 Codex 对话、当前代码和保留的评测结果由codex自动整理；部分中间评测文件已删除，其实验结论以当时的对话记录为依据。

## 1. 项目目标与初版

OpenWorkBot 面向个人和企业，目标是构建能够自主规划、调用工具和协作的智能助手。知识库首版参考 law 项目的 RAG 子图，但不引入其主图：独立 `rag/` 服务通过 MCP 供后台 Worker 使用，主助手保持对话响应。

初版使用 Milvus Cloud、Qwen3 0.6B 本地 Embedding 和重排模型，规划、证据判断及回答复用 Bot 的模型配置。流程为检索规划、查询生成、混合检索与重排、证据评估、回答；证据不足时最多补检一轮，不检查生成后的答案。

查询生成后来拆为重写、多查询、扩展、子问题拆分四个按需并行节点，混合检索与重排也拆开，以便分别调试和追踪。拆节点本身没有被证明能提高质量。

## 2. 首次评测与问题定位

选择 Bank RAG Benchmark 的中文银行文档与题目，使用 RAGAS 评分、Langfuse 跟踪。

2026-11-03 的端到端基线：50 题四项质量指标均有效，生成模型为 `gpt-6-luna`，裁判为 `gpt-6.1-terra`。

| 指标 | 结果 |
| --- | ---: |
| 文档 Recall@10 | 0.880 |
| 文档 NDCG@10 | 0.776 |
| Faithfulness | 0.710 |
| Answer Correctness | 0.473 |
| MCP 平均延迟 / P95 | 28.09 秒 / 35.47 秒 |

Answer Correctness 是自动评分，不是答对题目比例。

主要发现是：**命中目标文件不代表命中所需条款。** BF-001 找到目标文件，但材料清单和额度条款不全；BF-029 的关键块在合并候选中排第 47，当时重排候选上限为 32，关键块提前被截掉。讨论过将上限增至 64，但未证明该数值最优。

## 3. 离线解析与切块

原流程主要提取文本并按固定长度切块，容易切散标题、材料清单及金额条件。随后选择：

1. 用 `pdfplumber` 提取可识别的标题、段落、表格、图片区域、页码和位置，保存结构化 JSON；识别不到的结构不猜造。
2. 保守清理重复页眉、页脚和页码，业务警示至少保留一次。
3. 优先按标题、章节和段落切分，超长部分再拆；最终采用 **500 字符、重叠 50 字符**，不是讨论过的 512 Token。
4. 将标题路径和正文一起用于 Embedding、BM25 和重排，同时保留正文、章节与页码。

当时重建后的 100 份 PDF 生成了 100 份结构 JSON、1,277 个索引块。当前参数见 [rag_parameters.py](../../app/rag_parameters.py)，解析见 [structure.py](../../app/structure.py)。扫描件未接入 OCR，部分页面无可提取文本时不提供页级提示。

## 4. 父子检索与参数选择

BF-001 等问题的答案分散在文档的多个章节，仅返回少数片段容易漏信息。针对当时较短的银行文档，改为：

```text
检索规划 → 按需并行生成查询 → 向量检索 + BM25 → RRF 融合
→ 子块重排 → 按文档去重并回填全文 → 证据判断 → 回答
                                         └─ 不足时最多补检一轮
```

当前每轮最多 6 个查询，向量检索和 BM25 各取 20，每条查询 RRF 融合后取 10；合并去重后最多 20 个子块进入重排，按每份文档最高子块的重排顺序聚合，最多回填 5 份完整文档。实现见 [graph.py](../../app/graph.py) 和 [knowledge.py](../../app/knowledge.py)。

曾讨论先取重排前 10 个子块再聚合文档；若它们都来自同一份文件，其他相关文档会被截掉，因此选择先重排候选、再按文档聚合。也讨论过向量 0.6、关键词 0.4 的加权融合，但没有证据证明这组权重更优，当前仍使用普通 RRF，常数为 60。

父文档回填能补足分散条款，但长文档可能带入噪声或超出模型上下文，不能保证适用于所有资料。

## 5. 拆分评测

端到端分数难以区分检索失败与生成失败，后来拆成三层：

- **独立检索**：运行实际检索，统计文档召回、排序和耗时。
- **固定证据生成**：使用同一份证据生成和评分，便于比较提示词与模型。
- **端到端**：检查完整链路的回答与延迟。

生成评测不依赖 Langfuse；Langfuse 保留过程追踪，评分结果存本地，不回写评分。独立检索按开关决定是否上传完整过程和候选。脚本见 [evaluate_retrieval.py](../evaluate_retrieval.py) 和 [evaluate_generation.py](../evaluate_generation.py)。

文档召回仍不能确认关键条款完整。11 月 4 日的一轮检索中，47/50 题成功，平均 Recall@5 为 0.8736，但仅 31/47 题找齐全部标注目标；有些题标注了 6 或 7 份文件，最终最多返回 5 份，Recall@5 不可能满分。

## 6. 生成与评分中遇到的问题

### 引用影响评分

早期回答会自动追加全部检索文件，包括可能不适用或已废止的文件，既可能误导用户，也会被裁判视为额外事实。

对同样 5 个回答分别以完整回答和去除纯引用正文评分，各重复 3 次：正确性均分从 0.594 变为 0.693，忠实度从 0.710 变为 0.961。差额反映评分对引用文本敏感，不能直接算作回答能力提升。随后按用户选择，回答暂不展示引用编号和来源列表，证据仍用于生成、评分和按需追踪。

### 正确补充也可能被扣分

Answer Correctness 使用 75% 事实匹配和 25% 语义相似度；正确性评判主要比较回答与参考答案，不直接核对额外内容是否受原文支持。参考答案较短时，正确补充也可能被记作多余。

曾用 10 题已有回答对比 75/25、90/10、100/0，均分分别为 0.537、0.507、0.487。事实判断本身存在误扣，因此没有直接改为 90/10；分数下降也不能单独证明新权重更差。

### 提示词范围过宽或过窄

一次放宽回答范围后，50 题平均回答明显变长，正确性从 0.7527 降到 0.5683；既有合理补充被扣分，也有真实的规则适用错误。对照并非严格单变量实验，随后按用户要求回退提示词。

当前提示词强调直接回答，并保留影响结论的必要条件、适用范围和例外，见 [prompts.py](../../app/prompts.py)。即使目标文件已召回，仍可能漏答材料、混淆规则或把范围说得过于绝对。

### 题目与参考答案不一致

BF-040 原先只问项目文件，参考答案却要求完整开户材料；后来修改了问题。BF-024 的参考答案明确补充“小微企业优先”的条件。BF-012、BF-033、BF-004 等题也经过讨论和修订。

讨论过更贴近业务的评分口径：必答要点应覆盖，有依据的相关补充不扣分，错误或无依据的补充要扣分。该口径尚未实现为当前主指标；目前仍使用 RAGAS Faithfulness 和 Answer Correctness。

## 7. 可靠性与追踪问题

- BF-025 曾因查询生成的模型请求失败而无法检索；后来增加兜底：所有查询转换失败或为空时使用原问题，补检不重复执行已经检索过的查询。
- BF-001 曾在证据判断阶段因模型连接错误失败；RAG 模型及评测裁判对连接错误采用指数退避，最多重试 3 次。重试不能消除持续性的网络或服务故障。
- 原端到端评测需要等待 Langfuse 追踪可读取；拆开运行和评分后，可先继续后续题目。评分仍需读取相应证据，不能把后台上传等待简单等同于模型耗时。
