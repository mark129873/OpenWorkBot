# 主聊天与多助手技术设计（待审批）

本文件是设计草案，尚未实施。现有行为以 `architecture.md` 和代码为准；开发前需获得用户审批。

## 1. 范围与架构

- 一个持续的主聊天；主助手负责沟通、分配和判断，文件及命令工作由子助手执行。
- 单个 FastAPI 后端进程，`asyncio` 驱动主助手与最多 3 个通用子助手；关闭页面不停止工作，后端停止则中断。
- 使用现有模型、工具、SQLite 和 SSE；不增加任务表、Redis、Kanban 界面或长期记忆模块。保留现有 `todo` 用途，不以它调度后台任务。
- 参考 Hermes 的后台委派、边界投递和任务交接，不引入其 Kanban 内核；Hermes 普通后台委派的完成消息恢复不等于恢复运行中的子助手。

```text
主聊天 ← HTTP / SSE → FastAPI → 应用级 Runtime
                              ├ 主助手 Loop
                              ├ 调度器与消息路由
                              ├ 子助手 Loop × 0..3
                              └ SQLite：聊天、内部消息与上下文
```

`main.py` 的 lifespan 创建和关闭 Runtime，并持有执行任务引用；`api/chat.py` 提供新接口。Runtime 负责调度及投递，`agent/loop.py`、`agent/subtask.py` 执行模型循环；`sessions/store.py`、`replay.py`、`approvals.py` 负责持久化、投影和权限。前端改造现有聊天组件和流处理，不保留会话导航。

## 2. 数据与上下文

- 每个数据目录使用固定内部主会话 `Session.id = "main"`，启动时幂等创建；用户不选择会话。
- 复用 `Message` / `Part` 的 JSON 字段并扩展内部部件类型；内部记录标记为隐藏，不能出现在用户聊天或被误拼入主助手历史。

| 内部记录 | 最小内容 |
| --- | --- |
| 任务 | `task_id`、名称、目标、状态、创建顺序、负责人、当前 `run_id`、文件占用、停止意图 |
| 上下文 | 独立 `context_id`、所属任务、角色、原始模型消息与工具结果、摘要边界 |
| 消息 | `message_id`、任务及运行标识、发送方、接收方、类别、内容、关联请求和投递状态 |
| 审批 | `request_id`、任务及运行标识、工具、参数快照、授权范围、原因和处理状态 |

- 负责人上下文绑定 `task_id`；每次协助使用独立上下文。助手槽位可复用，但不能继承前一任务的上下文；`run_id` 防止旧运行的迟到结果影响新运行。
- 主对话、各任务分别组装和压缩模型上下文；主助手只接收任务关键信息及主动标记的重要消息，需要时可查询相关执行记录。工具调用与结果必须配对。
- 原始聊天、助手通信和工具返回值保留；摘要和裁剪只作用于模型输入副本，不再覆盖数据库中的旧工具结果。摘要失败不推进压缩边界。
- **待审批建议**：沿用现有工具截断行为，保存工具实际返回的内容；文件读取超过 6 万字符、命令输出超过 3 万字符时，截断前的前段不会保存。

所有状态写入通过单进程写锁和短 SQLite 事务串行化；每次事务使用独立 SQLAlchemy Session。序号分配、状态变更和消息写入须原子提交，不能在持锁时等待模型、命令或用户。沿用 WAL 与现有权限规则。

模型调用日志沿用现有快照机制，并发写入和轮转需串行，附任务及运行标识；日志写失败仍只告警，不阻断对话。

## 3. 调度与助手通信

- 任务状态：`queued → running`，`running ↔ waiting_user`，`running → reviewing`；主助手从 `reviewing` 决定重新排队、完成、失败或停止。停止意图先持久化，再协作式停止负责人及协助者。
- 队列按任务最初交代顺序分配；续跑沿用原顺序。等待用户确认的助手仍占名额。已完成任务可带原上下文继续；原助手忙时可由其他空闲助手接手。
- 主助手使用结构化任务工具创建、查询、修改、停止、继续和确认完成；子助手使用消息、查询同伴、请求协助及等待回复工具。工具调用只表示请求被接收，不表示接收方已处理。
- 每个助手有独立收件队列。消息先写入 SQLite 再唤醒接收方；接收方上下文写入与标记已投递在同一事务中完成，处理结果落盘后再标记已处理。重启补投未处理消息，按稳定消息 ID 避免重复插入上下文；任务 ID 和 `run_id` 防止错投，已落盘完成的工具按调用 ID 去重。
- 子助手可向正在工作的同伴询问已有信息；对方在当前操作结束后的安全边界处理。额外协助由系统原子分配给空闲助手；已有用户任务排队时优先处理用户任务，没有空闲助手时请求方自行继续。协助期间助手视为忙，A 可继续其他工作；原任务仍由 A 负责。
- 用户要求变更时同时通知负责人和协助者；停止时同时停止相关协助。已开始的命令沿用协作式停止，不承诺立即终止或撤销副作用。
- 子助手结束或达到单次 30 步上限后，主助手依据结果及按需查询的记录判断完成、继续或停止；可立即发起新一轮并重新计算 30 步，重复且无进展时可停止，不硬编码重复次数。
- 消息按类别将结果、失败及需决策事项送达主助手；子助手也可主动标记重要消息。其余同伴通信保留记录，不自动填满主助手上下文。

## 4. HTTP、SSE 与页面

| 接口 | 行为 |
| --- | --- |
| `GET /api/chat` | 返回主聊天快照、全部待处理审批、权限模式和主对话上下文用量；无模型配置时仍可加载 |
| `POST /api/chat/messages` | 接收客户端消息 ID、文本和可选权限模式；非空校验，重复 ID 相同内容幂等返回，不同内容返回冲突 |
| `GET /api/chat/events` | SSE：先注册订阅并发送一致快照，再推送消息、审批和用量更新；断线重连重新获取快照 |
| `POST /api/chat/approvals/{request_id}` | 接收现有 `option_id` 和可选拒绝理由；校验任务、运行和请求归属 |

保留 `/api/permission/state`，移除不再使用的旧会话接口及重新生成入口。SSE 使用独立订阅队列；注册订阅、取得快照及事件发布受同一写锁和版本序号协调，避免快照与增量之间丢事件。慢连接溢出时断开并以快照重连；消息按主助手实际发送顺序入库。流式正文分批保存后广播，打断和结束时先保存；前端按消息 ID 和版本更新，避免重连重复或缺字。

页面沿用左右消息布局、Markdown、空聊天引导、顶部助手名称及主对话用量，输入框保留权限模式选择；删除侧栏、任务详情、工具记录、复制、重新生成和停止按钮。任务相关的提问、进展、结果和审批均标明任务；审批展示操作、参数、原因及现有选项。回复默认简短，用户要求时可展开，不设固定字数上限。

用户始终可发送：新消息打断主助手回复，保留并标记已输出部分，丢弃旧轮次的迟到输出；用户输入优先，后台报告等当前回复及新消息处理后，按实际发送顺序追加。

## 5. 审批、冲突与恢复

- 新消息保存与暂缓全部待处理审批在同一事务完成，主助手结构化路由后：修改或停止目标任务时撤销该任务及协助者的旧审批；其他审批恢复。多条新消息均路由完成后才恢复其余审批。归属不明时保持暂缓并在聊天中询问；暂缓或撤销的审批提交返回冲突，不能执行。
- 存在待处理审批时，主助手先通过 `route_input` 工具给出消息涉及的全部任务和意图，再继续普通回复；模型调用需支持指定工具。缺少有效路由时不得自动放行；接口不支持时报告错误并保持暂缓。系统从运行时确定消息来源，子助手不能伪造用户或授权结果。
- 多个审批独立绑定任务、`run_id` 和请求 ID；延用仅本次、会话内和拒绝及其原有规则优先级。会话授权由全部任务共享，后端重启后按现有行为失效；尚未处理的审批重启后使用新 ID 重新发起，旧 ID 失效。
- 明确文件工具按解析后的真实路径协调：不同任务等待先占用该文件的任务结束；同一任务的协作者按单次写操作串行。Runtime 记录路径版本，若写入曾等待，或读取后文件被其他助手通过文件工具改动，拒绝旧写入并要求重新读取。相关文件操作实际结束、任务进入终态后释放占用。
- Runtime 将显式的消息回复等待和文件占用等待记录成有向关系；新增等待时检查是否成环，同一等待环只通知主助手一次并附任务及等待原因，由其判断如何处理，不自动终止。等待结束时移除关系，重启后根据持久状态重建。PowerShell 内部及未声明的依赖不可识别。
- 重启时恢复排队、运行、等待用户及待主助手判断的未完成工作；已完成、失败和已请求停止的任务不自动重跑。已完成但未投递的结果仍须送达主助手或聊天。
- 停机时正在执行但没有结果的工具，在恢复上下文中标记为结果未知，交给子助手自行检查并继续；不新增逐操作询问，也不把未知结果记为成功。任意命令无法保证恰好执行一次。
