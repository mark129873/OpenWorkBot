# 主聊天与多助手技术设计（待审批）

本文件是设计草案，尚未实施。现有行为以 `architecture.md` 和代码为准；开发前需获得用户审批。

代码结构、运行时和通信细节见 [多助手运行时与通信设计](multi-agent-runtime-design.md)。

## 1. 范围与架构

- 一个持续的主聊天；主助手负责沟通、分配和判断，文件及命令工作由子助手执行。
- 单个 FastAPI 后端进程，`asyncio` 驱动主助手与最多 3 个通用子助手；关闭页面不停止工作，后端停止则中断。
- 使用现有模型、工具、SQLite 和 SSE；不增加任务表、Redis、Kanban 界面或长期记忆模块。保留现有 `todo` 用途，不以它调度后台任务。
- 参考 Hermes 的后台委派、边界投递和任务交接，不引入其 Kanban 内核；Hermes 普通后台委派的完成消息恢复不等于恢复运行中的子助手。

```text
主聊天 ← HTTP / SSE → FastAPI → 应用级 Runtime
                              ├ 主助手 Loop
                              ├ 调度器与消息路由
                              ├ 子助手 Loop × 0..3
                              └ SQLite：聊天、内部消息与上下文
```

`main.py` 的 lifespan 创建和关闭 Runtime，并持有执行任务引用；`api/chat.py` 提供新接口。Runtime 负责调度及投递，`agent/loop.py`、`agent/subtask.py` 执行模型循环；`sessions/store.py`、`replay.py`、`approvals.py` 负责持久化、投影和权限。前端改造现有聊天组件和流处理，不保留会话导航。

## 2. 数据与上下文

- 每个数据目录使用固定内部主会话 `Session.id = "main"`，启动时幂等创建；用户不选择会话。
- 复用 `Message` / `Part` 的 JSON 字段并扩展内部部件类型；内部记录标记为隐藏，不能出现在用户聊天或被误拼入主助手历史。

| 内部记录 | 最小内容 |
| --- | --- |
| 任务 | `task_id`、名称、目标、状态、创建顺序、负责人、当前 `run_id`、文件占用、停止意图 |
| 上下文 | 独立 `context_id`、所属任务、角色、原始模型消息与工具结果、摘要边界 |
| 消息 | `message_id`、任务及运行标识、发送方、接收方、类别、内容、关联请求和投递状态 |
| 审批 | `request_id`、任务及运行标识、工具、参数快照、授权范围、原因和处理状态 |

- 负责人上下文绑定 `task_id`；每次协助使用独立上下文。助手槽位可复用，但不能继承前一任务的上下文；`run_id` 防止旧运行的迟到结果影响新运行。
- 主对话、各任务分别组装和压缩模型上下文；主助手只接收任务关键信息及主动标记的重要消息，需要时可查询相关执行记录。工具调用与结果必须配对。
- 原始聊天、助手通信和已采集的工具结果保留；摘要和裁剪只作用于模型输入副本，不再覆盖数据库中的旧工具结果。摘要失败不推进压缩边界。命令输出的采集上限见下方规则。
- 参考 Hermes 的 `read_file`：按行号和数量分段读取，默认从第 1 行开始、每次最多 2,000 行和 10 万字符；超限时告知截断及后续行号。单行超过 2,000 字符会截断，行内余下内容不能通过行号续读；原文件不变。
- 命令输出参考 Codex：流式采集每次最多 1 MiB，超限时首尾各保留约一半并标记省略量；继续读取进程输出以免阻塞，并保持字符编码完整。采集到的内容随任务记录保存，不额外生成输出文件或设置 7 天清理；模型每次最多看到 3 万字符的首尾预览，需要时可按工具调用 ID 分段查看本任务已保存部分。超过 1 MiB 的中间内容无法恢复；单次上限不限制长期累计存储。

参考源码：Hermes `9a76ac8e4f` 的 `tools/file_tools.py`、`tools/file_operations.py`；Codex `e72da2b538` 的 `codex-rs/core/src/unified_exec/`。

所有状态写入通过单进程写锁和短 SQLite 事务串行化；每次事务使用独立 SQLAlchemy Session。序号分配、状态变更和消息写入须原子提交，不能在持锁时等待模型、命令或用户。沿用 WAL 与现有权限规则。

模型调用日志沿用现有快照机制，并发写入和轮转需串行，附任务及运行标识；日志写失败仍只告警，不阻断对话。

## 3. 调度与助手通信

- 任务状态：`queued → running`，`running ↔ waiting_user`，`running → reviewing`；主助手从 `reviewing` 决定重新排队、完成、失败或停止。停止意图先持久化，再协作式停止负责人及协助者。
- 队列按任务最初交代顺序分配；续跑沿用原顺序。较早任务正在等待主助手判断时，较晚任务等待判断后再分配，已运行的任务不抢占。等待用户确认的助手仍占名额。已完成任务可带原上下文继续；原助手忙时可由其他空闲助手接手。
- 主助手使用结构化任务工具创建、查询、修改、停止、继续和确认完成；子助手使用消息、查询同伴、请求协助及等待回复工具。工具调用只表示请求被接收，不表示接收方已处理。
- 每个助手有独立收件队列。消息先写入 SQLite 再唤醒接收方；接收方上下文写入与标记已投递在同一事务中完成，处理结果落盘后再标记已处理。重启补投未处理消息，按稳定消息 ID 避免重复插入上下文；任务 ID 和 `run_id` 防止错投，已落盘完成的工具按调用 ID 去重。
- 子助手可向正在工作的同伴询问已有信息；对方在当前操作结束后的安全边界处理。额外协助由系统原子分配给空闲助手；已有用户任务排队时优先处理用户任务，没有空闲助手时请求方自行继续。协助期间助手视为忙，A 可继续其他工作；原任务仍由 A 负责。
- 用户要求变更时同时通知负责人和协助者；停止时同时停止相关协助。已开始的命令沿用协作式停止，不承诺立即终止或撤销副作用。
- 子助手结束或达到单次 30 步上限后，主助手依据结果及按需查询的记录判断完成、继续或停止；可立即发起新一轮并重新计算 30 步，重复且无进展时可停止，不硬编码重复次数。
- 消息按类别将结果、失败及需决策事项送达主助手；子助手也可主动标记重要消息。其余同伴通信保留记录，不自动填满主助手上下文。

## 4. HTTP、SSE 与页面

| 接口 | 行为 |
| --- | --- |
| `GET /api/chat` | 返回主聊天快照、全部待处理审批、权限模式和主对话上下文用量；无模型配置时仍可加载 |
| `POST /api/chat/messages` | 接收客户端消息 ID、文本和可选权限模式；非空校验，重复 ID 相同内容幂等返回，不同内容返回冲突 |
| `GET /api/chat/events` | SSE：先注册订阅并发送一致快照，再推送消息、审批和用量更新；断线重连重新获取快照 |
| `POST /api/chat/approvals/{request_id}` | 接收现有 `option_id` 和可选拒绝理由；校验任务、运行和请求归属 |

保留 `/api/permission/state`，移除不再使用的旧会话接口及重新生成入口。SSE 使用独立订阅队列；注册订阅、取得快照及事件发布受同一写锁和版本序号协调，避免快照与增量之间丢事件。慢连接溢出时断开并以快照重连；消息按主助手实际发送顺序入库。流式正文分批保存后广播，打断和结束时先保存；前端按消息 ID 和版本更新，避免重连重复或缺字。

页面沿用左右消息布局、Markdown、空聊天引导、顶部助手名称及主对话用量，输入框保留权限模式选择；删除侧栏、任务详情、工具记录、复制、重新生成和停止按钮。任务相关的提问、进展、结果和审批均标明任务；审批展示操作、参数、原因及现有选项。回复默认简短，用户要求时可展开，不设固定字数上限。

用户始终可发送：新消息打断主助手回复，保留并标记已输出部分，丢弃旧轮次的迟到输出；用户输入优先，后台报告等当前回复及新消息处理后，按实际发送顺序追加。

## 5. 审批、冲突与恢复

- 新消息保存与暂缓当时已有的待处理审批在同一事务完成；判断期间新产生的审批按现有规则提出（本次设计建议，待审批）。主助手结构化路由后：修改或停止目标任务时撤销该任务及协助者尚未处理的审批；其他暂缓审批恢复。多条新消息均路由完成后才恢复其余暂缓审批。归属不明时保持原有暂缓并在聊天中询问；暂缓或撤销的审批提交返回冲突，不能执行。
- 识别新消息期间，已获授权且无需审批的后台操作继续按原规则执行；主助手判断后再通知相关任务停止或修改，已开始或已完成的操作不承诺撤销。
- 存在待处理审批时，主助手先通过 `route_input` 工具给出消息涉及的全部任务和意图，再继续普通回复；模型调用需支持指定工具。缺少有效路由时不得自动放行；接口不支持时报告错误并保持暂缓。系统从运行时确定消息来源，子助手不能伪造用户或授权结果。
- 多个审批独立绑定任务、`run_id` 和请求 ID；延用仅本次、会话内和拒绝及其原有规则优先级。会话授权由全部任务共享，后端重启后按现有行为失效；尚未处理的审批重启后使用新 ID 重新发起，旧 ID 失效。
- 明确文件工具按解析后的真实路径协调：不同任务等待先占用该文件的任务结束；同一任务的协作者按单次写操作串行。Runtime 记录路径版本，若写入曾等待，或读取后文件被其他助手通过文件工具改动，拒绝旧写入并要求重新读取。相关文件操作实际结束、任务进入终态后释放占用。
- Runtime 将显式的消息回复等待和文件占用等待记录成有向关系；新增等待时检查是否成环，同一等待环只通知主助手一次并附任务及等待原因，由其判断如何处理，不自动终止。等待结束时移除关系，重启后根据持久状态重建。PowerShell 内部及未声明的依赖不可识别。
- 重启时恢复排队、运行、等待用户及待主助手判断的未完成工作；已完成、失败和已请求停止的任务不自动重跑。已完成但未投递的结果仍须送达主助手或聊天。
- 停机时正在执行但没有结果的工具，在恢复上下文中标记为结果未知，交给子助手自行检查并继续；不新增逐操作询问，也不把未知结果记为成功。任意命令无法保证恰好执行一次。

## 6. 实现约定补充（待审批）

- **记录身份**：任务、执行上下文、消息、审批和文件占用均有稳定 ID；关联 `task_id`、`context_id`、`run_id`，内部记录放入现有 `Message` / `Part`。可变状态及版本作为恢复依据，原始消息单独保留。
- **任务与执行单元**：根任务状态与每个负责人、协助者的运行或等待状态分别记录。根任务 `waiting_user` 表示有待确认事项，不代表全部执行单元暂停；等待用户的执行单元仍占用名额，其他执行单元可继续。负责人结束后，主助手判断前可有协助尚未结束，但完成任务前须收口相关协助。
- **状态迁移**：创建任务时持久化初始顺序；领取时原子写入负责人、上下文和新 `run_id`。30 步耗尽或负责人汇报后进入 `reviewing`，主助手可按原序重新排队。停止先落盘，再等待相关执行单元在安全边界收口；终态及停止意图在重启后不自动重跑。
- **执行单元状态**：记录 `running`、`waiting_user`、`waiting_reply`、`waiting_file` 及完成、失败、停止；等待中的单元仍占用槽位。根任务可从 `running / waiting_user` 进入 `reviewing`，再由主助手决定排队、完成或失败；任一未完成状态可请求停止。
- **消息与操作的事务边界**：消息写入和任务变更原子提交；投递时同一事务写入接收方上下文及投递状态，处理完成后记录结果和处理状态。已提交的内部任务操作按上下文、运行和 `tool_call_id` 去重；外部工具先记录运行中，结果落盘前中断则恢复为结果未知，不承诺恰好执行一次。
- **主回复被打断**：已提交创建的后台任务继续运行；尚未执行的调用不再执行。恢复模型历史时，丢弃未完整解析的工具调用；对完整调用保留已完成结果，或补齐中断结果，避免工具调用和结果失配。
- **等待环**：持久化执行单元之间的回复等待及文件等待；文件等待关联占用任务及可释放占用的执行单元。每次等待关系变更时检查有向环，附等待原因通知主助手；恢复后依据记录重建。
- **聊天接口契约**：快照包含消息、审批、权限模式、上下文用量和持久递增版本；SSE 增量携带版本、事件类型及对应数据。消息客户端 ID 相同且内容相同时幂等，不同时返回冲突；审批暂缓、失效或归属不匹配时拒绝提交。
- **恢复验收**：覆盖任务创建已提交但结果未送达、消息已投递但未处理、命令进行中断电、审批暂缓时重启、快照和事件交界处断线；要求任务不重复创建、消息不重复插入、未知结果不当作成功。另验证旧任务续跑优先于新排队任务、一个协助者待确认时其他执行单元继续，以及后台报告追加在新消息之后。
- **新消息与已授权操作**：主助手判断消息期间，已获授权的后台操作按原规则继续；判断为修改或停止后，先记录目标任务的变更或停止意图并通知相关执行单元。未开始的旧操作在安全边界重新判断，已开始的操作不强制中断。待处理审批仍按第 5 节暂缓。

## 7. 数据与接口格式（待审批）

- 内部 `Part.data.type` 区分 `task_state`、`agent_context`、`agent_run`、`agent_message`、`approval`、`file_wait`；记录携带版本与所属 `task_id`，执行和投递记录附 `context_id`、`run_id`。独立上下文消息标记为内部，回放和主模型历史均按上下文隔离。
- `task_state` 保存目标、创建顺序、根任务状态、负责人和停止意图；`agent_context` 保存独立上下文及摘要边界，`agent_run` 保存执行状态和步数；`agent_message` 保存来源、接收方、类别、内容、关联请求和 `pending / delivered / processed` 状态；`approval` 保存调用、参数快照、状态及授权范围。文件占用和等待边保存关联任务、执行单元及路径。
- `GET /api/chat` 返回 `{revision, messages, approvals, permission_mode, context_usage}`；`POST /api/chat/messages` 接收 `{client_message_id, text, permission_mode?}`，相同 ID 和内容重试返回原结果，内容不同返回 409。
- SSE 先推送 `snapshot`，随后推送 `{revision, type, data}`；类型包括 `message`、`approval`、`usage`。版本只对用户可见事件逐个递增并在事务内持久化；客户端按 ID 和版本更新，版本不连续、慢队列溢出或断线后重新获取快照。
- `POST /api/chat/approvals/{request_id}` 接收 `{option_id, feedback?}`；暂缓、失效、重复提交或归属不匹配返回冲突，停止状态优先于授权。重启后待处理审批用新 ID 发起，旧 ID 不再生效。
- `route_input` 结果包含用户消息 ID、涉及任务和意图；一个消息可含多个意图，无法确定时要求澄清。Runtime 对明确的修改或停止意图同事务记录动作并撤销受影响审批，再通知目标上下文。工具输出按任务及输出记录 ID 分段读取，仅允许主助手和所属任务的执行单元查看。
