# DeerFlow 协调器详细设计（草案）

状态：用户已确认保留 README 中的主 Agent、后台 Worker 和 2.1 通信架构，以 Agent Teams 示例为基础，沿用现有前端；成功、失败和停止任务的结果送达主聊天后清理调度数据、不归档，保留聊天结果、文件及不含任务内容的请求 ID 去重标记。提示 Worker 简短回复，超过单条消息 16 KiB 时截断并提示。取消团队累计 100 个请求和共享状态 20 条上限；重置当前用户所有 Agent / SubAgent，删除旧聊天、任务、检查点、长期记忆和模型日志并使用新会话。每次新 Run 刷新记忆。以下具体机制是候选设计，尚待批准和验证；总体边界见 [deerflow_design.md](deerflow_design.md)。

## 1. 组件与数据归属

    用户 ↔ 现有前端 / Gateway ↔ 主 Agent（独立上下文）
                                     ↕ 提交任务 / 运行反馈
                            协调器 / Runtime
                                     ↕ 调度 / 生命周期 / 并发
                        后台 Worker × 多个（各自独立上下文）

    主 Agent + 各 Worker ↔ Shared State（任务 / 进度 / 结果）
    主 Agent + 各 Worker ↔ Message Bus（请求 / 事件 / 通知）
    应用状态和重要消息 + 各 Agent 检查点 → 同一 SQLite 文件

主 Agent 理解用户目标、拆解与汇总；Worker 后台调用模型和工具。主 Agent 与 Worker 使用 Gateway 完整 `AgentRuns`，分别保存上下文；主回复结束或被新消息打断不取消后台 Worker。运行时控制任务调度、生命周期和并发。各 Agent 显式读写可恢复的 Shared State，通过 Message Bus 定向传递或发布订阅请求、事件和通知。DeerFlow 原生 `task`、`batch_task` 不直接替代本协调器：前者受父 Run 约束，后者可能在租约过期后重试。

| 数据 | 建议归属与标识 |
| --- | --- |
| 助手 / 成员 | 用户 ID、助手 ID、团队 ID、主线程 ID、工作区 ID；每个 Worker 上下文有独立线程 ID。标识由服务端创建并校验归属。 |
| 任务 / 执行 | 任务 ID、目标、顺序、状态、负责人、线程 ID、运行 ID；任务状态与待发送消息在一个业务事务保存。 |
| 共享状态 | 任务、进度和结果由主 Agent 与各 Worker 显式读写并可恢复；沿用 Teams 的来源和版本校验，共享内容不作为系统指令。 |
| 消息 / 投递 | 消息 ID、发送方、用户 / 团队、正文、目标或主题；每个接收目标独立保存投递 ID、目标线程、目标 Run 和状态。 |
| 工具操作 | 用户、运行 ID、工具调用 ID、参数及状态 / 结果；已有结果直接复用，结果未知的已开始操作不自动重跑。 |
| 重置 | 用户、助手、重置 ID、记忆代号和阶段；状态落 SQLite，用于失败重试和重启恢复。 |

应用表是任务、消息和用户可见聊天的事实来源；对应图检查点负责 Agent 模型上下文。Teams、Gateway 和检查点共用同一个 SQLite 文件，但各自连接不共享事务；DeerMem 文件和 FTS 仍独立。首版单 Gateway 进程，SQLite 只做短事务。

## 2. 调度与消息（待批准）

1. 用户输入主聊天；主 Agent 受理任务后，协调器保存任务和消息，再用稳定请求 ID 创建 / 启动独立 Worker Run。关闭页面或主回复结束不取消 Worker。
2. 消息发布时确定接收成员，在同一业务事务保存消息和各目标投递记录；协调器写入与总线必须共用该事务，不能仅依赖数据库文件相同。进程信号仅用于唤醒。发布后新加入的成员默认不追收旧消息，可读取共享状态。
3. 目标 Run 正在执行时，优先通过 `AgentRuns.send_input(..., mode="steer")` 投递；调用前持久化目标 Run 和请求 ID。接受请求不等于消息已应用：只在确认对应检查点已记录输入后标记已投递。
4. 失败重试使用相同目标 Run 和请求 ID；只有确认未应用才转交新 Run。若无法判定是否应用，保留待核查状态，不向新 Run 盲目重发。工具副作用同样不承诺恰好执行一次。

DeerFlow 单个 Run 最多接收 16 条输入、单条 16 KiB、总计 64 KiB；默认线程输入查询仅列最近 10 个 Run 的最多 32 条。建议扩展按用户、Run 和输入 ID 精确查询的内部能力：查询结果中“没有该项”或标为 `not_applied`，都不能单独证明未应用，仍需核对检查点；容量不足时保留总线待处理记录并反馈。具体接口和边界需验证。

## 3. 重启恢复与授权（待批准）

- DeerFlow Gateway 启动时将未完成的旧 Run 标为错误；Teams 示例重启后还需用户重连。不能假定图检查点或 SQLite 自动恢复 Worker。
- 建议借鉴 Gateway 的原生批任务授权快照：任务受理时由服务端保存用户 ID、账户版本和权限上限，不保存浏览器 Cookie / Token。重启后重新读取用户和当前权限，与原上限取交集；授权失效则任务等待用户处理。
- 对已完成且结果落盘的任务补投报告；只在检查点和工具记录证明安全时尝试恢复。已开始但结果未知的工具操作停止并提示检查，排队且尚未执行的操作重新检查授权。不可自动把异常当成功或重跑未知副作用。
- 批任务的 `restore_batch_authority` 限定原生批任务来源，不能直接视为 Teams 的现成恢复接口；需要 Gateway 为协调器提供受限恢复能力，并验证异常 Run 的图恢复入口。

## 4. 工作区（待批准）

- 不复用主 Agent 的 LangGraph `thread_id`：每个 Agent 的检查点、技能视图和运行身份保持独立。建议以服务端绑定的用户 / 工作区 ID，将各 Agent 的 `/mnt/user-data` 映射到同一所属工作区；不接收客户端自报的工作区归属。
- 建议共享工作区的实际文件目录独立于各 Agent 可删除的线程目录；删除旧线程时只删除线程私有数据。实际目录布局和权限检查待批准。
- DeerFlow 的 `ThreadDataMiddleware`、`SandboxMiddleware`、`LocalSandboxProvider` 和上传 / 产物接口均按线程派生路径；需一起适配，并保留各 Agent 的技能投影、租约和资源归属校验。不能只改一处路径或复用沙箱 ID。
- 共享文件的并发修改沿用现有项目的文件冲突协调语义；所有文件操作经用户归属、真实路径和权限检查。不向 Agent 暴露宿主命令工具，包括旧 PowerShell 工具；MCP 和自定义工具的能力不由该开关保证。
- 助手重置保留所属用户工作区；Windows 路径、符号链接、文件锁和稍后 Docker 切换均需独立验证，当前只设计 LocalSandbox。

## 5. 任务与 Teams 容量（方向已确认，机制待批准）

- 成功、失败及停止的任务，在结果送达主聊天后清理调度数据、不归档；聊天结果及工作区文件保留，只留下不含任务内容的请求 ID 去重标记。移除团队累计 100 个请求及共享状态 20 条的上限。
- 示例不会自动删除已结束的请求，并把整个团队写在单条 JSON 中；按新要求清理后，已结束任务不再长期累积。仍未结束的任务和去重标记可能增多；建议先沿用示例存储形式，验证性能后再决定是否调整，具体方式待批准。
- 示例还把所有共享状态限制在 16,000 字节内，完整共享上下文限制在 24,000 字节内；只取消 20 条限制仍可能拒绝新增。需将状态存储与模型输入预算分开，并支持按需分页；具体接口待批准。
- Teams 示例最近消息只保留 100 条，同一根请求最多关联 12 个请求；这些限制独立于已取消的两项上限，是否调整须另行确认。
- 一个任务可能关联多个 Teams 请求和回执；团队快照接口的偏移量最多 200，历史接口仍声明 100 条请求上限。取消总数限制时需一起适配存储、查询和去重；任务状态与待发送消息仍使用同一业务事务。
- 候选：清理前先完成结果投递并处理相关依赖 / 回执；清理与写入去重标记使用业务事务。重复请求不能重新执行，同一 ID 参数不一致时如何校验需进一步确定；去重标记本身随请求增多而增长。
- 用户选择提示 Worker 简短回复，超过 DeerFlow 单条输入的 16 KiB 限制时截断并提示；不采用结果 ID 和分段读取。Teams 示例在 6,000 UTF-8 字节处截断的行为需调整。
- 候选：按 UTF-8 字节计算完整消息的大小，为消息包装和截断提示预留空间，在字符边界截断。单个 Run 的累计输入上限和输入条数上限仍须通过待处理队列处理；具体方式待批准。

## 6. 重置与长期记忆（范围已确认，机制待批准）

1. 重置按认证用户隔离：停止当前用户所有 Agent 和 SubAgent 的运行；删除其旧聊天、任务、检查点、模型日志，并清除该用户全部 Agent 的长期记忆。其他用户不受影响，工作区保留。已开始的外部操作需先收口；结果未知时保持重置未完成并提示核查，不自动重跑。
2. 建议给用户设置持久代号；由服务端在 Run 受理时记录代号。重置开始时阻止该用户旧代写入，避免迟到的旧运行、检查点写入及记忆提取重新生成已删数据；记忆提取提交前须在同一用户的写入 / 重置互斥边界检查代号。具体屏障和收口方式待批准。
3. 取消该用户记忆队列中待处理项，再调用 `clear_memory(user_id=当前用户, agent_name=None)` 清除摘要及所有 Agent 事实。确认旧记录和记忆清除成功后，各 Agent 使用新的空白线程；未加载旧检查点或旧聊天。
4. 清除失败或进程中断时，保留重置阶段并幂等重试；不得提前报告完成。清除开始前允许取消重置，开始清除后不可承诺恢复已删除的数据，此交互需确认。

DeerMem 的队列上下文目前没有记忆代号，且 `cancel_by_agent` 不能取消已经开始的提取；停止 Agent 并不能保证已开始的提取停止。上述代号与写入屏障需要新增适配，必须覆盖普通提取、摘要前冲刷和事实增删改等写入口。

DeerFlow 的记忆快照会写入检查点。按已确认方案删除当前用户全部旧检查点、使用新线程且不回放旧聊天后，新会话不会从旧检查点恢复这些快照；仍需处理已在途的旧提取和迟到写入。

DeerFlow 默认仅在会话首次运行时注入记忆快照；用户已选择每次新 Run 刷新。建议读取当前用户及 Agent 已落盘的记忆并替换旧注入快照，不能覆盖用户消息或叠加旧快照；提取异步进行，刷新不能保证立即看到刚产生的事实。具体实现及读取失败处理待批准。

DeerFlow 的线程删除会删除线程目录，而其默认工作区在该目录下；此外检查点、Run 和事件删除失败可能只记日志。不能直接用该接口承诺删除成功或保留工作区，需适配并逐项检查结果。候选：先按用户列出旧线程及其日志，在删除所属关系前持久化无正文的清理清单，失败后按清单重试，完成后移除清单；具体流程待批准。

DeerMem 的索引更新失败可能只记日志并标记待修复；不能仅凭 `clear_memory` 返回值认定索引已清除，需要验证当前用户的索引状态及失败恢复。

现有模型调用日志包含完整消息，按会话写文件但没有用户标识；用户已确认重置时删除该用户旧模型日志。多用户下如何确认日志归属并覆盖轮转文件，需设计和验证。

DeerMem 默认 `strict_user_scope: false`，部分运行时缺失身份会退回 `default`。多用户场景建议在所有入口传递并校验认证用户，拒绝缺失身份，并启用严格用户作用域作为额外保护；仅打开配置不足以防止 `default` 回退。

DeerMem 注入当前用户共享摘要和当前 `agent_name` 的事实；Worker 的线程 ID 与记忆里的 Agent 名称不是同一概念。动态 Worker 如何对应 Agent 名称及事实桶尚未确定，不能仅凭线程隔离推断记忆隔离。

## 7. 前端与源码接入（待批准）

- 沿用 Vite 前端；建议 Gateway 增加兼容现有主聊天快照、消息、审批、上传、重置和 SSE 的接口，将主聊天和后台报告投影到现有界面。备选是改前端直接消费 Gateway 原生线程 / Run 接口；实际改造量尚未验证。
- 增加 DeerFlow 本地账户登录 / 注册；保留其 Cookie 与 CSRF 防护，状态变更请求携带 `X-CSRF-Token`。重置确认需明确提示删除当前用户旧聊天、任务、检查点、模型日志和所有 Agent 的长期记忆，并保留工作区。
- 候选源码布局：把固定版本 DeerFlow Gateway、harness、extension API 和 Teams 示例收编到正式 `backend/`，移植本项目协调逻辑；合并后端依赖及锁文件，保留现有前端，按 MIT 保留必要版权与许可。启动入口从 `app.main:app` 调整为 Gateway。具体目录、依赖和原有代码保留方式未批准。
- 本机静态文件清单中两个后端有相同的 `pyproject.toml`、`uv.lock` 和空 `app/__init__.py`；不能直接覆盖前两个文件。正式运行不能依赖未入库的 `.github_deerflow` 参考目录。
- DeerFlow 的 `DEER_FLOW_HOME` 与 `database.sqlite_dir` 分别决定运行数据和 SQLite 位置；建议明确配置到项目数据目录，并核对工作区、记忆和索引的实际路径。开发时清空数据目录与助手重置保留工作区是两种操作，不能混用；目录布局待批准。

## 8. 需要验证

- 用户授权撤销、账号禁用、服务重启和断线后的 Worker 恢复；未知工具结果不重跑。
- 同一 / 不同用户的定向与广播、6,000 字节以上结果的发送及 16 KiB 截断、检查点与消息状态之间的崩溃；超过 20 条及 16,000 字节的共享状态按需读取；请求去重与取消累计上限后的性能。
- 记忆刷新与异步提取的时序；旧代提取跨越重置、全部旧线程删除、迟到写入、其他用户同时写记忆、清除中故障 / 重启、FTS 同步失败和重置取消边界。
- Windows 下独立线程共享工作区、跨用户文件访问、上传 / 下载、同文件并发写入和禁止宿主命令。
- Gateway 登录、Cookie / CSRF、现有前端 SSE 和主聊天审批；测试使用隔离空库，RAG 不纳入本次验收。
